# SWD 真实负载与 WCH-LinkW 对照：结论及改进可行性

日期：2026-10-24。评估对象：CH570Q 固件 1.3.2、WCH-LinkW 固件 2.0.0。本总结依据已有上板记录、保留的 JSON 结果和当时源码。

**后续状态：**1.3.3 已实现发送看护、从机响应门控及显式重连，原生/构建通过；**2026-10-25 已上板复测**（[1.3.3 上板验收](v133-hardware-validation.md)）：下文描述的连续块读永久静默与 GDB `load` 失败在 1.3.3 上没有复现（fb 30 min / 2214 cycle 零超时、GDB 8×1 KiB 40 轮全过、GDB `load` 5/5），但真实故障后的恢复路径未被驱动、强杀客户端仍会卡死主机。下文为改进前的实测结论与可行性评估，实施状态和超时响应协议勘误见 [重连实现说明](reconnection.md)。

## 1. 结论

**CH570Q 已证明基本 SWD 功能和混合负载下的数据正确性，但尚未达到可依赖的日常调试器水平。当前首要障碍是连续块读触发后不能自行恢复，其次才是吞吐与尾延迟。继续投入软件修复有明确依据，现有证据尚不支持先换芯片或重做射频硬件。**

- 混合负载三组各 120 s 全部通过，覆盖真实 AP 访问、Flash 块读、暂停/恢复、寄存器读取和 RAM 写入回读恢复。这证明功能链路成立；不能据此宣称现场故障已解决。
- 连续同类块读仍在约 4–24 s 内触发永久静默；真实 GDB `load` 两次中一次失败，并留下 Flash 擦空、CPU lockup 的现场。1.3.2 的重传预算修复解决了一类问题，但没有覆盖这个失效路径。
- WCH-LinkW 在同形 GDB 连续 8×1 KiB 读取中 5/5 通过，也有 15/15 次 `program`+`verify` 成功记录。因此，连续读取导致永久失联并非无线 SWD 必然存在的限制，本项目实现仍有改进空间。
- WCH-LinkW 的原始 DAP 压测也出现请求无响应、主机等待 5 s 超时；后续运行无需拔插即可继续。它仍有停顿问题，但本轮表现出的恢复能力明显强于 CH570Q。

当前使用定位：适合受控实验和短时调试；连续内存观察、无人值守烧录、依赖 GDB `load` 的流程尚不能作为可靠使用场景。已成功的 OpenOCD 擦写路径可以作为临时入口，但不构成烧录可靠性验收。

### 2.2 与 WCH-LinkW 的对照

| 场景 / 指标 | CH570Q 1.3.2 | WCH-LinkW 2.0.0 | 可得结论 |
| --- | --- | --- | --- |
| cycle，100 kHz，Bulk 单独 | 8.3 cycle/s | 正常完成的短轮约 23.4–28.7 cycle/s | 同口径吞吐约差 2.8–3.5 倍 |
| cycle p99 | 67.23 ms | 正常轮约 10.2–20.2 ms | 正常轮尾延迟约差 3.3–6.6 倍 |

| 15 字块读 p50 | 约 38–41 ms | 约 7.4–8.1 ms | 块读约差 5 倍 |
| GDB 连续 8×1 KiB 读 | 已复现约 24 s 失败 | 5/5 通过，首轮 6.03 s，后四轮 3.13–3.37 s | 此场景稳定性有实质差距 |
| 原始 DAP 连续块读 | 可在约 4 s 后永久静默 | 5 轮中 3 轮跑满、2 轮因 5 s 超时中止，后续可恢复 | WCH-LinkW 也会停顿，但无需断电恢复 |
| 故障后恢复 | 清 fault / 换 USB 传输仍可能无效，需要相关板复位 | 后续轮次无需拔插即可正常 | 恢复能力是最优先补齐的差距 |

上述 WCH-LinkW 正常轮延迟没有包含失败请求的 5 s 主机等待，不能把这些数字理解成其所有请求都低于几十毫秒。调查记录统计 16 轮中 5 轮出现无应答；轮次长短、命令分布和提前退出不同，不能据此推导长期失效率，或和 CH570Q 的 120 s 零故障直接比较。

CH570Q+CDC 的 5.6 cycle/s 与 WCH-LinkW 单独运行相比约差 4–5 倍，但这不是同等并发条件。本轮没有 WCH-LinkW 的 UART 并发对照，不能判定两者无线串口能力的优劣。

烧录方面，WCH-LinkW 在 1 MHz 下 10/10 成功、中位 14.45 s，100 kHz 下 5/5 成功、中位 15.28 s。CH570Q 的成功记录是 `flash write_image erase`+`verify_image`（约 10.9 s），GDB `load` 是 1/2 成功。**这些命令路径和样本口径不同，不能合并成同一烧录成功率，也不能据 10.9 s 对 14.45 s 宣称 CH570Q 烧录更快。** WCH 记录的 ELF 文件大小 116180 B 也不等于实际烧入 Flash 的有效字节数。

证据：[WCH 1 MHz 烧录](../build/flash-compare/linkw-20261024/summary.json)、[100 kHz 烧录](../build/flash-compare/linkw-100khz-20261024/summary.json)、[GDB 五轮连续读](../build/gdb-dump-stress/linkw-20261024-205152/summary.json)、[完整对照与边界](bulk-cdc-investigation.md#13-与-wch-linkw-的对照复测2026-10-24)。

## 3. 主要缺点的改进可行性

下面的“高/中”表示根据代码结构和已有现象作出的初步工程判断，不表示已经烧录验证。

| 优先级 | 缺点 | 初步可行性 | 预期收益 | 工作量 / 风险 |
| --- | --- | --- | --- | --- |
| P0 | 射频发送状态永久忙 | 高，但 SDK 停止/回调语义需验证 | 一次丢完成事件不再导致永久静默 | 中；旧回调与 DMA 复用竞态 |
| P0 | 从机待发送响应阻断所有收包 | 高 | 保留重传应答能力并恢复 HELLO/收包服务 | 小至中；必须保留去重缓存 |
| P0 | 请求超时后 fault 永久锁存 | 中 | 失败能明确上报，下一会话可重新连接 | 中至大；写入结果不确定、不能盲重放 |
| P1 | RX 重挂失败难观测、无有界恢复 | 计数扩展高，自动恢复中至高 | 区分发送卡住、接收失效与普通丢包 | 小至中；统计兼容与恢复节流 |
| P1 | 原始 SWD 读序列后需补线复位 | 高，但修改位置需按原始序列语义核实 | 消除对当前工具补偿行为的依赖 | 小至中；不能擅加时钟或抢占目标驱动 |
| P2 | 块读慢、服务期间产生额外重传 | 中至高 | 降低内存窗口读取时间与无效 RF 流量 | 中至大；AP posted read 和 WAIT 错误语义 |
| P2 | CDC 并发放大延迟 | 中至高 | 改善交互延迟和 UART 并发体验 | 中；吞吐、公平性与丢日志之间取舍 |

### 3.1 发送看护：最值得先做

[radio.c](../src/radio.c) 的 `sending` 由发送开始置位，仅在完成/超时回调或启动失败时清除；没有前台超时回收。实测“故障窗口 tx 不增长、清 fault 后仍无效、复位恢复”与该路径吻合。

建议增加独立前台 `radio_poll(now)`，主从都调用，即使会话 fault、没有新请求或从机卡在待应答分支也必须运行。记录发送开始时间，超限后进入恢复状态；100 ms 可以作为初始候选值，最终阈值应依据真实发送完成时延确定，不能把目标 SWD 服务时间误当作单帧 RF 发送时间。

**不能只执行 `sending=0; start_rx()`。** 要先确认底层发送停止，处理或隔离旧 IRQ/回调，再复用 `tx_dma`；`RFRole_Stop()` 失败时不能宣布 idle。恢复失败应有计数、节流与升级路径，必要时才评估射频重新初始化或整机看门狗。纯清软件标志可能导致 DMA 仍在使用的缓冲被覆盖。

可确定的是当前缺少有界退出；“究竟是完成中断未到、事件竞争还是 RF 库状态异常”仍未证明。`tx_count` 在发送完成回调才增长，所以零增量不能单独证明没有调用 `RFIP_StartTx`；现有计数也未直接捕获故障瞬间的从机门控值。WCH RF 库为预编译代码，停止与迟到回调语义需通过头文件、官方样例和上板插桩共同验证。

### 3.2 从机响应门控与会话恢复：分两层做

[app.c](../src/app.c) 的 `slave_poll()` 在 `pending_response` 时只尝试发送并立即返回；发送一直失败便不再取请求。可增加有界等待，超限后释放待发送门控、允许继续收包，但保留 [link.c](../src/link.c) 的 `last_request`、`last_response`、`next_sequence`，让同会话同请求重传只重发缓存响应。

先修物理发送恢复，再设计 fault 恢复。超时只证明主机没收到结果，不能证明目标没执行：RAM/Flash/外设写入甚至带读副作用的寄存器访问都有重复执行风险。不能简单清 fault、创建新 HELLO 后自动重发旧请求；新 HELLO 会清掉从机缓存并重置 DAP 状态。

可行的第一阶段是：同会话内保留去重并尝试取回原响应；超过事务预算则向调试软件明确报告失败，允许随后显式重新连接，并丢弃旧会话迟到响应。自动续传及 GDB 下载事务恢复属于更大范围的工作。当前 GDB `load` 的失败还需独立回归，不能承诺射频看护一项就能治好。

### 3.3 诊断与 SWD 序列：成本较低，适合伴随 P0 做

把现有 `rx_timeouts` 暴露给管理工具，并增加发送忙持续时间、看护触发/恢复成功/失败计数；最好提供最近一次失败的角色、阶段、session/sequence。采用版本化统计或新增子命令，避免直接改变旧客户端固定解析的 12 字段。

[swd.c](../src/swd.c) 的原始读序列以输入态结束，后续事务依赖额外线复位的现象已复现。但 `DAP_SWD_Sequence` 是原始引脚序列接口：**不能直接在每个输入片段后强制驱动高或补 2–3 个时钟**，否则可能改变调用者要求的连续输入、turnaround 与目标驱动阶段。应核对捕获脚本是否正确表达完整事务及 turnaround，在合理边界修正方向交接；分别测试连续输入片段、输入转输出、无额外线复位后接普通 DP/AP 访问，并用逻辑分析仪确认无争用。

### 3.4 性能：先减少额外事务，再测量 GPIO 时序

[dap.c](../src/dap.c) 的 `read_reg()` 对每个 AP read 都立即追加一次 DP RDBUFF。15 字 AP 块读因此通常需要 30 次物理读事务。对于可流水的连续读取，可改成一次启动、连续取前一次返回值、末尾一次 RDBUFF，理想情况下由 30 次降至 16 次。**这是物理事务量约减半的机会，不是端到端速度翻倍的承诺。** 需覆盖 WAIT/FAULT、部分完成计数、最后一字、AP/DP 混合与写后完成检查；建议先只优化 `DAP_TransferBlock`，降低影响范围。

工具配置 100 kHz→1 MHz 时，块读 p50 仅由约 40.9 ms 降到 28.9 ms，说明配置频率与端到端性能并非线性关系。GPIO 函数、逐半周期计时、中断、RF 往返及额外 RDBUFF 都可能贡献开销；**没有实际 SWCLK 波形和分段计时，不能断言固定开销的具体占比。**

服务时间感知的重传也值得做：20 ms 的 RTO 下限低于当前块读服务时间，35–38% 的重传比例不能解释为空口丢包率。可在保持 1500 ms 事务预算与足够发送机会的前提下，按命令类别/实测服务时间设置保守等待，避免响应尚在生成就密集重传。CDC 合并轮询、限制空轮询与调度份额可随后评估；先补较高 UART 负载的数据，再设限额。

## 4. 建议实施与验收顺序

1. **先补观测和射频恢复**：主从独立前台看护、Stop/旧回调处理、RX 重挂失败恢复、计数器。用故障注入覆盖不来完成回调、停止失败、迟到回调和重挂失败。
2. **再补从机与会话退出路径**：待响应门控有界释放、保留缓存去重、明确向上报告结果不确定。用执行计数验证丢响应重传时写操作只执行一次；覆盖主从分别复位和迟到响应。
3. **以原故障用例验收恢复**：连续 fb 块读主从都不永久静默；建议至少 30 min，再跑 20 轮 GDB 8×1 KiB；分别注入主从故障，检查恢复无需拔插、结果不伪成功、失败不重复写入。时长与轮数是下一轮建议门槛，尚未完成。
4. **独立验收烧录**：两探头用同一镜像、相同速率和同一 OpenOCD 命令重复比较；CH570Q 的 GDB `load` 单列测试，每次都写后逐字节校验并检查 CPU 可恢复运行。出现一次失败应保留完整日志与射频现场，不能靠重试吞掉失败。
5. **稳定后再优化性能**：固定时长、同时统计正常请求延迟、失败请求等待和恢复耗时；先做 AP 块读流水，再做服务时间感知重传、CDC 调度及 GPIO 优化，逐项 A/B。

**下一版最有价值的目标：连续内存读取不再导致永久失联，偶发错误有明确结果并能恢复连接。达到这一点后，再追赶 WCH-LinkW 约 3 倍的同口径混合负载吞吐和约 5 倍的块读性能。**
